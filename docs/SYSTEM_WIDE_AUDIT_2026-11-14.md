## Findings and priority

P1 means a release blocker because of account integrity, pending-work loss, record duplication or materially stale operational data. P2 means a reproducible correctness/performance issue requiring correction or explicit acceptance. P3 denotes a defensive guard or conditional risk without an established production failure. These are application findings; they do not imply that an attacker has compromised production.

## Further security and operational risks

- **Logout and copied bearer tokens:** `server/security/token.js` issues seven-day tokens with no per-token/session identifier. `/auth/logout` destroys the cookie session; it does not revoke an individual opaque bearer token. A copied bearer token remains subject to expiry, active-account/role/platform checks and `authVersion`, but logout alone does not change those checks. This is a confirmed design property requiring a session-termination policy; a live stolen-token scenario was not exercised. Preserve other devices by using server-owned per-installation/session revocation rather than globally revoking all users on every logout.
- **Dependency advisories:** lockfile audits report server **7** (6 moderate, 1 low), Web **1 high** (`vite`), Mobile **11** (4 high, 6 moderate, 1 low), Cloudflare **0**. Mobile high entries include Expo tooling, `node-forge`, `re2js`, and `zod`. The existing local forge patch addresses one verification issue, not every current advisory. Vite/Expo tooling advisories do not establish an exploitable installed APK or production static site. Reachability and supported dependency updates require review. No blanket `npm audit fix` was run. Evidence: `output/system-audit-2026-11-14-dependencies.json`.
- **Free-hosting capacity:** the backend uses one named Durable Object. Representative report, backup, authentication and notification workloads still need CPU/memory/subrequest measurement. Its cache is bounded by entry count rather than total bytes. A07 proves avoidable database calls, not a measured production outage. Workers and Durable Objects have different CPU rules; applying the regular Worker's 10 ms budget to every Durable Object request would be incorrect. See [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) and [Durable Object limits](https://developers.cloudflare.com/durable-objects/platform/limits/).
- **Background wake amplification:** the Worker wakes durable background jobs for every unsafe HTTP method, including rejected requests and read-only notification POST queries. That classification is broader than the API's corrected mutation classification. Review scheduling after the correct authorization boundary while preserving the pre-commit recovery guarantee; do not remove durable delivery intent.
- **Notification retention:** events/deliveries contain `deleteAfter`, but these collections are not in the checked-in explicit cleanup policies and no matching TTL settings appear in `firestore.indexes.json`. Whether production has separately configured TTL policies was not verified. Expiry filters prevent showing old events, but do not themselves delete expired infrastructure documents.

## Controls inspected without a demonstrated bypass

The review covered the route/middleware permission chain; account versions, platform restrictions and assignment authorization; login/recovery/verification; canonical record mutations and receipt/version checks; offline draft/outbox ownership and takeover conflicts; price publication and notifications; QR/report handling; cache/subscription lifecycle; backup authorization/encryption; Firestore rules; and the Cloudflare gateway/background lifecycle.

The API uses a deny-by-default permission map and live authorization checks, with bounded authorization caches. Record mutation services retain version/receipt/ownership checks. Checked-in Firestore rules deny direct client document access, and private credentials are excluded by the existing build/audit controls. QR verification is server-authoritative. The single Cloudflare API authority retains one revision fanout path. No proven arbitrary role escalation, direct client Firestore-write bypass or QR-signature forgery was found in the reviewed paths. That is not a claim that every production configuration or attack path has been certified.

Actual Firebase-deployed rules/IAM, physical notification permissions/delivery, shared-network beneficiary load, provider outages, backup restoration at representative volume, and real signed-in multi-role device workflows were not exercised. The review did not use production credentials to impersonate users.

## Local corrections already prepared

### Database / schema

No schema, role, business-record or retention changes were made. Pending offline records remain account-scoped. A01/A09 corrections do not delete existing production data.

### Server / API

`server/routes/auth.js` now separates invalid Firebase token errors from infrastructure failures. Only errors during actual ID-token verification can be classified as token rejection; failures after a token was verified, including server credential/token-construction errors, return retryable 503. This avoids clearing a valid account during service outages without accepting unauthorized requests. Firebase documents the distinction in its [Admin Authentication error reference](https://firebase.google.com/docs/auth/admin/errors).

### Mobile

- `mobile/src/data/dataStore.js`: one shared hydration promise; restoration waits for hydration; duplicate restoration callers share one promise; startup/default-guest persistence is suppressed; login/logout wait for hydration; scoped drafts are restored; temporary read failures remain retryable. An already-blank profile can be recovered online through the existing server-verified Firebase session. Missing/incorrect offline authentication is not bypassed.
- `mobile/src/services/storageService.js`: opt-in strict hydration propagates device-read failures instead of converting them into missing credentials.
- `mobile/src/services/authService.js`: login reports a failed token save instead of falsely completing.
- `mobile/src/screens/auth/SplashScreen.js`: retry feedback for storage/restoration failures; MainTabs requires an actual account identity.
- `mobile/src/navigation/RootNavigator.js`: missing identity redirects to Login rather than exposing the default guest profile as a signed-in account.
- Mobile app/package/lock metadata is locally 1.1.1. This is preparation only.

### Web

The initial audit left Web corrections open. The subsequent local patch now isolates dashboard/registry read failures, honors cooldowns, preserves publication intent and guards QR previews. See [AUDIT_RECOVERY_FIXES_2026-11-14.md](AUDIT_RECOVERY_FIXES_2026-11-14.md) for current changes and tests. The download manifest still targets the published 1.1.0 APK.
